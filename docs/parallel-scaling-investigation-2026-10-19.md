# 并行探索低加速比调查（2026-10-19）

调查基线是 `d9b499b`，生产 tracer SHA256 为 `4d908a2e…`。本轮保持生产源码不变，
使用已有万状态实验、离线日志分析和隔离调度变体确认原因。

主要原因是**协调器串行处理完整快照闭包，包含验证和持久化屏障**，并叠加可避免的派发等待。
任务分配确实不均，但单独均衡分配的收益明显小于消除派发等待。以下区分实际测量、
源码机制与尚未实施的优化；不把增加 worker 数量等同于增加有效计算量。

## 1. 已有大图结果和调查方法

三节点 Raft 库案例，pages/depth12/budget2。已有 24 次独立 Session 测量全部通过：
每次 10,457 节点、18,266 唯一边且恰好 18,266 次边尝试、零重试、完整带标签图一致。

| workers | DFS 中位秒 | BFS 中位秒 | DFS 加速 | BFS 加速 |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 613.756 | 583.575 | 1.000× | 1.000× |
| 2 | 509.259 | 499.995 | 1.205× | 1.167× |
| 4 | 478.141 | 471.115 | 1.284× | 1.239× |
| 8 | 489.166 | 479.368 | 1.255× | 1.217× |

这是相对并行框架自己的 1-worker。独立冷原生 DFS 为 34.241 秒、27,247 次转换，
其新增保存节点集合与并行搜索一致，但原生保存的边投影只含 first-parent，执行次数也不同，
不能据此构造同逐边工作量的速度比。之前报告保留了全部重复、时间漂移和覆盖范围。

本轮把 `parallel.cpp` 复制到 `build/parallel-cause-analysis/`，链接同一套既有 NP3 对象，
仅替换协调器对象，构建四个带相同计时探针的隔离 binary：

- measured：原有调度规则；
- poll0：成功派发一个任务后，以零超时 poll 检查结果；未派发时仍允许等待；
- rotate：仅轮转派发扫描的起点，收包顺序保持原样；
- both：上述两项组合。

保留每轮最多一次上传、完整消息处理、模型校验、快照闭包校验、持久化、重试和搜索规则。
每轮独立启动并先计时 parallel，之后运行本地原生 oracle；跨 binary 再比较完整规范化图。
关闭 memfd 传输，启用默认 resident-memory 路径；不变更宿主 ASLR。

诊断 binary 的精确源码和编译/链接命令、SHA256 记录在 `variants.json`。这里只把调度顺序
作为实验因素，未将这些变体替换为生产实现，也不据案例图相同声称一般模型语义已经证明。

## 2. 协调器是同步的中心服务站

```mermaid
flowchart LR
    A[协调器：导出完整闭包并上传 Task] --> B[worker：导入并同步、恢复、枚举与保存]
    B -->|零条或多条 Edge，最后 Done| C[协调器：逐帧收包、验证、导入并同步]
    C --> D[Done 后向 frontier 提交后继]
    D --> A
```

每个 worker 可以独立枚举，但协调器的发送、完整收包和逐边 import 都在同一个线程中执行。
[`parallel.cpp:298`](../src/core/search/parallel.cpp#L298) 派发第一个任务后即结束派发扫描；
`:343` 接收完整消息，`:386` 同步调用 `import_bundle`；后继到 Done 阶段才提交。
在处理一个 worker 的完整帧或导入时，协调器不能同时服务其他 worker。

`import_bundle` 的成本不只是登记一个 hash：

1. 对所有提供的 blob 重新 hash；
2. 对本地已有对象读取并比较字节，再逐对象调用 save；
3. 重新验证完整引用闭包；
4. 等待 blob 持久化，再发布 metadata 并同步。

见 [`snapshot_bundle.cpp:61`](../src/core/state/snapshot_bundle.cpp#L61)。因此已有对象去重
并没有免除搬运、比较、闭包遍历或同步屏障。单纯增加执行 worker 不会并行化这条中心路径。

## 3. 调度对照：等待有因果贡献，公平性不是主要解释

先用 depth8 的同一案例做 2×2 对照：每轮 1,138 节点、1,934 次转换，全部完整图一致。
顺序为 measured/poll0/rotate/both，随后反向 both/rotate/poll0/measured，减少单向时间漂移影响。
本轮因果对照仅针对这个BFS案例，不把改进幅度直接赋给DFS或其它程序。

| 变体 | 两次完整命令秒 | 派发后 poll 累计秒 | worker 任务分布 |
| --- | --- | --- | --- |
| measured | 25.503 / 26.013 | 5.607 / 5.682 | 第一次 worker1=650、worker8=11 |
| poll0 | 19.975 / 20.022 | 0.0056 / 0.0059 | 第一次 worker1=196、worker8=29 |
| rotate | 24.666 / 24.526 | 4.124 / 3.932 | 每个 worker 约 140–146 个 |
| both | 19.907 / 19.647 | 0.0058 / 0.0054 | 每个 worker 约 138–145 个 |

仅取消成功派发后的等待，重复得到约 22% 的耗时下降。第一次完整耗时差为 5.528 秒，
派发后实际 poll 等待差为 5.601 秒，且 import 基本不变（12.481 对 12.698 秒）。
这支持该等待是实质损耗。poll 经常会被就绪 FD 立即唤醒，**不能推导全局 50 tasks/s 硬上限**。

轮转派发让任务分配接近均匀，但单独仅降低约 4.5% 的中位耗时；组合结果与 poll0 接近。
因此“任务数不均”有明确的调度原因，却不足以解释大部分吞吐损失。

第一次对照的协调器墙钟分解进一步表明中心服务成本没有随等待消失：

| 阶段 | measured 秒 | poll0 秒 |
| --- | ---: | ---: |
| import，包含验证和持久化等待 | 12.481 | 12.698 |
| poll，总计 | 5.722 | 0.153 |
| 完整 receive | 2.895 | 2.961 |
| Task 上传 | 1.751 | 1.723 |
| 闭包 export | 1.725 | 1.589 |

消除派发等待后，import 单项仍占完整命令的约63.6%。如果保持这项服务成本不变，即使
理想地消除其它全部开销，19.975秒也不能低于12.698秒，进一步提升最多约1.57×。
这是相对本轮8-worker的条件性上界，还没计其它协调器工作；不是对所有程序的Amdahl常数。

没有探针的生产版本控制轮为 23.991 秒；它和 measured 的差异不足以单独估计探针开销。
以上因果比较采用相同探针的变体，不能直接把实验变体耗时当作生产优化承诺。

### 万状态确认

同一 depth12 万状态图的 measured 与 poll0 已分别通过本地原生 oracle 和完整图比较。
两者都是10,457节点、18,266次转换、零重试，并与先前24轮的规范化图签名相同。

| 项目 | measured 秒 | poll0 秒 |
| --- | ---: | ---: |
| 完整命令 | 231.487 | 190.458 |
| import，含验证与持久化等待 | 122.701 | 123.717 |
| 总 poll | 40.636 | 0.207 |
| 其中派发后的 poll | 40.066 | 0.051 |
| 完整 receive | 28.837 | 28.332 |
| Task 上传 | 15.972 | 15.616 |
| 闭包 export | 14.697 | 14.368 |

完整耗时减少41.029秒（17.72%，约1.215×），派发后等待减少40.015秒，import基本未变。
消除这项等待后，import仍占约65.0%。保持其成本不变，即使其它耗时全部消失，相对当前
8-worker也最多再提升约1.54×；实际还必须支付其他串行服务成本。
大图只测了一对，不能把17.72%当作所有运行条件下的稳定中位收益；它与短实验的反向重复
及实际等待分解相互印证，而不是仅凭两次总耗时推断原因。

### 计时口径

探针记录协调器单线程各调用的墙钟时间，包含被阻塞的时间，并非 CPU 百分比。
`poll` 包含 `post_dispatch_poll`，后者又包含 `post_dispatch_idle_poll`，三者不能相加。
“存在空闲 worker”没有证明当时一定存在符合 BFS 门控的可派任务。
`poll_timeouts` 还包括零超时 poll 返回0，不能解释为20ms等待次数。
每个 worker 的延迟从上传完成后到协调器消费 Done，不含上传，包含协调器服务延迟，
不能当作 worker 的执行时间。

## 4. 任务粒度让大量成本用于无转换任务

24 份 journal 的离线对账确认，BFS 每轮 10,457 个任务中：

- 3,824 个任务产生转换；
- 6,633 个任务零产出，占 63.43%：4,270 budget 截断、2,363 depth 截断；
- 深度12的 4,134 个任务全部零产出，最终类型遵守 budget 优先于 depth 的规则。

[`worker.cpp:75`](../src/core/search/worker.cpp#L75) 先 import、准备线程、adopt、恢复完整快照，
随后 [`scheduler.cpp:722`](../src/core/scheduler.cpp#L722) 才按已保存的 metadata 判定失败、
terminal、budget 或 depth 截断。无转换任务因此仍支付输入闭包和恢复成本。
63.43% 是任务数量比例，**不能将其当作耗时比例或承诺消除同等比例的运行时间**。

BFS 每轮协调器收发约 76.335 GB；每个任务平均发送 2,657,909 字节，每条边平均接收
2,657,471 字节，总传输摊销为 4,179,082 字节/边，含协议控制开销。
累计 counter 没有逐任务字节归属，无法精确计算零产出任务单独浪费的字节数。
这些是协调器端点单边计数，不再把双方计数相加造成重复。

## 5. BFS 层屏障和负载偏斜的范围

BFS 层宽为 1、5、11、19、35、75、151、296、545、957、1615、2613、4134。
只有前两层合计6个任务的宽度天然不足8；各大层观察到的峰值在途租约可以达到8。
所以“整个图太窄”无法解释整体偏斜。

[`frontier.cpp:90`](../src/core/search/frontier.cpp#L90) 要求最浅 Pending/Inflight 层结束后
才能派发更深节点，每层尾部必须等最慢 source。再加上 Done 后才提交后继，限制了流水线。
本轮保留这个 BFS 语义，没有把取消层屏障当作性能优化。

原有 BFS8 三次中 worker1 分到 2,370–2,454 个任务，worker8 只有 60–73 个。
按 lease/edge/done 事件次数加权，在途租约均值约4.43–4.50；满8只占0.57%–0.73%的事件。
在途租约可以包含等待收发或 Done 尚未消费的任务，事件统计也不是时间采样，
不能称为平均只有4.5个 worker 在 CPU 上运行。

## 6. 持久化等待与环境波动

此前独立可靠无栈 perf 窗口约20.067秒：协调器 fsync 10,335 次累计6.193秒，
fdatasync 2,067次累计2.039秒；worker 合计另有2.741秒和0.994秒。
这是框架 snapshot store 的宿主持久化调用，与目标程序模拟的网络或文件系统调用不同。

fsync:fdatasync 恰5:1，与 blob store 的四个 fsync 加 metadata 的一个目录 fsync 和
一个 fdatasync 对应。见 [`state_store_packed.cpp:369`](../src/core/state/state_store_packed.cpp#L369)
及 [`sysstate_store.cpp:220`](../src/core/state/sysstate_store.cpp#L220)。这是聚合与源码的对应，
无栈录制没有证明每个调用的具体 callsite；不同线程等待也会重叠。

### 原生与并行的同步粒度不同

原生 `sys_state::save_metadata()` 仅检查并追加 metadata，未逐状态调用 flush；
`StateStore::save` 接受不可变对象，`wait_for_completion` 才确认持久化。
普通搜索可以从 pending/cache 或进程可见的已写文件读取，段轮换、显式屏障及退出另行同步。
见 [`state.cpp:250`](../src/core/state/state.cpp#L250) 和
[`state_store.h:65`](../src/core/state/state_store.h#L65)。

并行的通用 `import_bundle` 则在每次 Task 和 Edge 导入后执行 blob 屏障与 metadata 屏障。
因此原生与并行除了搜索次序和工作量不同，**还采用不同的同步频率**。BFS 10,457 个Task
加18,266个Edge就是28,723次导入。由这条正常路径推算，合计约请求172,338次同步系统调用，
不含初始化、轮换、退出及EINTR重试；这是源码推算，不是本轮全程 syscall 计数。
传输了重复对象仍会经过屏障，不能因去重命中就假设它免费。

worker 的输入副本与协调器发布给全局 frontier 的状态，可能不需要相同的掉电持久性。
这是值得明确拆分的契约：worker 失败可以由协调器已有状态重试，而全局已确认状态和反例
必须遵守发布保证。可以研究“进程内可读”和“已持久发布”的不同接口；不能在现有通用
import API 中直接省略屏障并继续沿用原来的成功含义。

旧大图资源观测中8-worker整树平均约1.61核、峰值PSS约503MB。
本轮3秒宿主采样中CPU约87%–88% idle、无swap、无网卡丢包，NVMe flush await约0.5ms。
另一次在途快照确认37个owned进程均允许使用CPU0–11，沿cgroup祖先未设CPU quota；
这排除了该快照时刻被限制在一两个核心的配置解释，不等于实际利用了12核。
这个窗口横跨生产控制轮的搜索收尾与后置校验，不能用它估算8-worker稳态利用率。
此前较慢测量窗口的 flush await为2.09–2.40ms，说明必须保留时间漂移，但这些不同时间的
窗口不能证明整批耗时变化均由磁盘延迟造成。

CPU 样本的 import25.50%、wire22.94%、restore/adoption21.54%、export13.10% 也显示，
大量计算用于状态处理；CPU样本不包含睡眠，不能替代本轮协调器墙钟计时。
曾丢失38.57%样本的 DWARF syscall 录制不用于上述延迟结论。

## 7. 优化优先级和需要保留的契约

1. **成功派发后先零超时 drain，再继续填充 worker。** 对照已证明局部收益；生产修改还需
   worker loss、deadline、取消及图等价回归。轮转可以改善公平性，但独立吞吐收益较小。
2. **在已验证的保存状态上提前分类零转换任务。** 避免完整传输和恢复；共用分类规则，
   保留失败/terminal/budget/depth优先级，明确损坏快照和不支持恢复的错误契约。
3. **降低协调器 import 服务成本。** 只传缺失对象、复用已验证不可变依赖、避免 owning
   Bundle 反复物化与全闭包遍历。memfd 只改变搬运媒介，当前仍做这些工作，既有对照反而退化；
   不能把换成共享内存当作自动解决中心串行路径。
4. **设计批量持久化与发布。** 可以研究一组边的 staging/validation 后一次屏障，再发布
   metadata/完成确认。错误仍必须传播，失败 store 必须保持 poisoned，已确认反例必须能在
   worker 丢失后恢复。直接删除 fsync 或 clean flush 会改变当前故障检测契约。
5. **在中心服务率提高之后再评估更粗任务和层内调度。** 让 worker 保持更多局部状态、
   批量返回结果；相同 source/action 的确定性、全局去重、租约重试及 witness 链仍需验证。
