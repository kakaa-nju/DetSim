# 用户态与内核态的扩展成本（2026-10-24）

原生主机的并发 IPC 下降不是内核路径独有：本轮用户态 IPC 下降比内核态更大。
这不支持仅围绕 `/proc`、ptrace 系统调用数量解释全部损失，但也没有定位到某个
C++ 函数或证明硬件上限。

沿用[缓存事件实验](native-cache-counters-2026-10-24.md)同一原生 Ryzen 5 2600
主机、冻结 product-placement 二进制、输入和 depth12 图。每个 1/6/12-worker
配置分别运行 `{cycles:u,instructions:u}` 与 `{cycles:k,instructions:k}`，各一次。
FIFO 计数窗口仍为原生 parallel 命令及收尾，不包含 prefix/串行参考，覆盖
协调器、初始 tracees 和继承的 worker/tracee 子树。

| 指标 | 1 worker | 6 workers | 12 workers |
| --- | ---: | ---: | ---: |
| 用户态指令/边，百万 | 5.3840 | 5.6405 | 5.8224 |
| 用户态周期/边，百万 | 4.0548 | 4.8033 | 7.0110 |
| 用户态 IPC | 1.32781 | 1.17431 | 0.83047 |
| 内核态指令/边，百万 | 1.3708 | 1.4804 | 1.5506 |
| 内核态周期/边，百万 | 2.4903 | 2.8875 | 3.7680 |
| 内核态 IPC | 0.55044 | 0.51268 | 0.41151 |

1→12：用户态指令/边约 +8.1%、周期/边约 +72.9%；内核态指令/边约 +13.1%、
周期/边约 +51.3%。用户态执行每条指令的成本增长同样需要解释，不能把所有
guest/native on-CPU 成本增加当作内核 syscall 或锁等待。

这些计数来自不同运行，不能将两组周期直接相加并当成同一次测量的精确分摊。
软件 task-clock、上下文切换及迁移仍是整个进程的计数，不是对应特权态的耗时。
一次/配置不足以建立置信区间，也不构成无插桩性能排名。12 workers 使用这台
机器的 12 个逻辑 CPU，只有 6 个物理核；结果不直接移植到 gpunode 的 WSL。
缓存延迟、SMT 竞争、前端/后端执行资源和指令组合变化仍有待区分。

## 采集与验证

最初四个硬件事件同时成组的探测返回 not counted，保留 NMI watchdog=1，
没有修改系统设置。拆成两个双事件组后探测可用。六次真实运行的所有请求事件
均有效、running fraction=1，原始事件明确保留 :u/:k，未混淆过滤器。

六图均为 10457 节点、18266 边/尝试边、零重试，规范图摘要相同；输入哈希、
原始 stat.jsonl 重解析、启停 ACK 时序、receipt 与计数 manifest 核验通过。
第一版私有 wrapper 未传播 main 返回码，随后修正；首个运行的独立 manifest
及原始计数也完整通过，因此没有用 wrapper 的退出码替代计数有效性验证。

证据在 `build/shared-parallel/native-privilege-counters/`，主核验为 `audit.json`。
只改私有采集 wrapper，没有修改产品、系统配置或引入依赖。审计后删除可再生
快照及重复 worker 二进制，保留原始计数、报告、图和配置并再次核验。
