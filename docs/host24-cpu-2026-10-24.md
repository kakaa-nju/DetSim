# WSL 12/24-worker 的宿主运行量（2026-10-24）

24 workers 确实使用了更多宿主 vCPU，但本轮搜索期间没有持续占满 24 个。
这说明不能把增加 workers 后的低收益简单说成“完全没用上更多核”，也不能仅凭
这组窗口样本精确分解每任务成本或剩余等待。

## 方法与结果

使用当前冻结 typed-pool 基线、Raft-library depth16、pages/shared、BFS、
same-cpu、seed1、100 rounds，各一次 12/24-worker 采样，顺序执行。
磁盘恢复后原有 WSL→Windows PowerShell 互操作可用，复用既有交互式采样器，
没有新建跨机器时钟换算。先通过三次空闲采样；十二项分析测试及四项 phase
wrapper 测试通过。

每次请求保留 guest 单调时钟边界、host QPC 查询边界及 provider 自身 timestamp。
只接受确定处于 CLI parallel 命令内的完整相邻样本区间。VM 运行率由 24 个具名
Hyper-V VP 的原始累计计数及各自 base 差分得到，排除 _Total，不猜物理核编号。
零逆序、零计数回退、零无效区间，runtime 分量闭合检查通过。

| 指标 | 12 workers | 24 workers |
| --- | ---: | ---: |
| 原生 search seconds（诊断） | 17.65094 | 15.92879 |
| CLI 命令窗口，秒 | 17.87814 | 16.16155 |
| 接受的完整区间数 | 12 | 11 |
| 覆盖时长，秒 | 16.27024 | 15.14050 |
| 命令窗口覆盖率 | 91.01% | 93.68% |
| 按时长加权忙碌 VP 数 | 11.8400 | 17.2478 |
| 忙碌 VP 数中位数 | 11.8533 | 17.7472 |
| 覆盖区间内 VM 运行量，VP·秒 | 192.6397 | 261.1403 |
| 宿主忙碌 CPU 加权性能指标中位数 | 104.867% | 104.239% |

更多 VP 正在运行，但吞吐收益比忙碌 VP 数的增幅小。这里的 VM 运行量包含
coordinator、workers、tracees 和 guest 内核，不是 worker-only 计算时间。
两个覆盖窗口不同，不能把覆盖 CPU 直接除以全部图的边数来宣称每边 CPU 成本。
性能指标只是 Windows provider 的上下文指标，不是精确的逐 worker 实际频率。
本轮不把 raw wait 字段转换成新的等待时间结论。

## 验证与限制

两次均为 63418 节点、112305 边/尝试边、零重试，完整图 SHA256 同既有基线。
原始 samples、phase、journal、图、配置及结果取回本机后重新核验通过，采样器
正常结束，无错误记录。所有输入摘要一致；实际 hot/warm cache 为 32/64 MiB。
没有同时运行其他 CPU 实验，没有改变宿主电源、affinity、ASLR 或内核设置。

采样有开销，各配置一次，不能用于稳定性能排名；上表原生 search seconds 与
包含收尾日志的 CLI 命令窗口不同，不能混用。空闲/忙碌由 host 计数器定义，
on-CPU 不等于有效指令执行。不能将旧版本 1-worker 数据拼接成当前的精确分解。

下一项应补完整命令窗口中协调器与已回收 worker/tracee 的 CPU 用量，以区分
协调器饱和、CPU 成本增加和可用并发不足。无需为此立即删除任何状态/线程检查。

证据位于 `build/shared-parallel/host24-cpu/`，主审计为 `audit.json`，保留
`evidence/{sample12,sample24}/analysis.json` 的所有接受/排除区间。归档验证后
清理本批可再生快照和重复 worker 二进制，保留原始采样和图验证证据。
