# 不可变 resident 页表整块复用实验（2026-10-23）

结论：候选通过下述正确性与搜索图验证，但没有稳定的全链路性能收益，暂不合入。
这不证明所有工作负载都无收益，也没有改善接近线性加速的证据。

## 改动与正确性边界

原实现仅从仍有效的 `entry.image` 整块复用 Pages；候选改为从不可变
`entry.object_hint` 复用。两端必须为 page 格式、映射文本及 region 几何相同、
PageRef 数量和全部字节相同。否则仍走已有逐页重建。没有合并 reserve 或 status
reader 候选，没有改动失效、live-memory 判断、捕获、恢复、页内容或状态身份。

新的复用只是把已有的逐页相同对象复用合成整张描述符表复用。live image 失效
后 object_hint 本来就可保留不可变对象；新捕获/恢复仍负责建立新的 live proof。
root、brk 和新快照保持新值。独立审查未发现新增阻断问题。

私有候选在 `build/shared-parallel/resident-page-table/`，二进制 SHA256 为
`feabfca516a2a5a062bf7c020f1476c1447fc20a6db1c81952b2a7cc974bce5a`。
NP3 重编译一个 TU；NP2 从一致冻结源码重编译全部 TU，用扩展 capture fixture
验证普通/tiny-cache 下的全量字节 oracle。基线正常模式通过；要求整块复用时，
基线实际因 `whole immutable page table reuse expectation differs` 失败；候选
两种缓存模式通过。修改目标页后必须换表；只改模型元数据则必须改变 snapshot
root，但仍复用相同页表。跨 root 补测由 `recheck_np2.py` 完成并记录源码摘要。

7 项 NP3 native gates 全通过（20.959 秒）。独立 depth12 参考为 10457 状态、
18266 边/尝试边、零重试，完整图文件重新哈希与既有参考一致。这些是 scoped
捕获/恢复和搜索图证据，不是任意外部内存修改或任意运行时的安全证明。

## WSL depth16 两轮对照

固定 Raft-library、pages/shared、BFS、seed1、same-cpu、1/12 workers。基线
复用前次已验证的参考，候选生成自己的独立参考；两轮交错顺序。10 个结果均为
63418 状态、112305 边/尝试边、零重试，所有完整图文件独立重算摘要相同。

native 搜索命令耗时（秒）：

| 轮次 | workers | 基线 | table | 耗时变化 |
| --- | ---: | ---: | ---: | ---: |
| 0 | 1 | 158.19717 | 159.51582 | +0.83% |
| 1 | 1 | 156.15508 | 145.84411 | -6.60% |
| 0 | 12 | 18.56232 | 18.88404 | +1.73% |
| 1 | 12 | 20.19885 | 20.12045 | -0.39% |

两轮方向不一致。12-worker 中位数 19.38058 → 19.50224 秒；加上延后关闭为
20.27211 → 20.39389 秒。单 worker 的 157.17613 → 152.67996 秒不能被解释为
稳定收益；候选自身跨轮也有较大变化，没有同步资源数据来确认原因。
搜索加关闭仍是两个不连续时间段之和，不包括串行 oracle/验证总运行时间。

`build/shared-parallel/resident-page-table-wsl/audit.py` 核对输入、配置、结果、
时间加法关系并重算10份完整图。基线参考来源报告摘要单独核对；五项输入传输
前后摘要一致，三项私有挂载卸载成功，没有本次进程和宿主 rootfs 子挂载残留。
原始命令、图与审计结果保留在该目录。

## 下一步诊断

最近的 FD reader、reserve 和整表复用均没有可靠改善扩展效率。继续堆局部
小改动不足以解释并发时增加的 CPU 成本。下一项控制将使用真实 worker journal
中的 guest CPU0,2,…,22，对比纯计算及不同工作集/共享方式的依赖内存访问。
它测量独立固定工作任务的聚合吞吐，不是 DetSim 固定总搜索图的加速比，也不
构成硬件上限；仍需用真实搜索验证任何后续实现。

另一个共享页 pin 争用假设已降低优先级：已有任务内 DWARF 样本中，W1/W12
pin_user_pages_remote 为41/42，read_regions占5.48%/5.36%，不支持其为主要
CPU增量来源。相关草稿未编译运行，不能作为实验结果。
