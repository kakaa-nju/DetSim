# WSL 计算与工作集控制实验（2026-10-23）

结论：同一 CPU 分配下，不同固定工作负载的并发扩展差异很大。不能把此前约
8倍的独立搜索吞吐当作机器统一上限，也不能把共享表的12倍当作 DetSim 已达到
线性。下一步需要延长纯计算控制并比较 guest CPU 分配，结合真实搜索判断。

## 范围与验证

这是独立进程的固定工作量控制，不运行 DetSim、ptrace 或目标程序。每个 worker
先完成输入、表验证和 CPU 绑定，再等待 ready/go；计时内只有算术或依赖读取。
CPUs0,2,…,22 来自真实12-worker搜索的 worker_spawn journal，而非猜测拓扑。
单 worker 使用CPU0。guest affinity 不能证明 Windows 上固定的物理核关系。

计算为8条独立uint64算术链，读取为随机单环uint32表的 index=next[index]。
文件映射与每进程私有缓冲区使用同一个表文件、同一操作次数；共享不是页pin
实验，计时循环没有process_vm_readv。输入字节数为32KiB、8MiB、64MiB。

使用 `/usr/bin/g++ -std=c++20 -O3 -fno-tree-vectorize -Wall -Wextra` 编译。
反汇编保留8条乘法链循环及依赖加载循环。8项短测试通过：计算、已知4节点环的
共享/私有读取、损坏环拒绝、NaN/Inf超时拒绝、实际运行超时、SIGTERM后回收所有
观察到的worker。工作进程无孙进程；Popen/pidfd用于归属清理。辅助实现会话已归档。

两轮反向case/worker顺序，共24次运行。`audit.py`独立核对所有原始worker JSON、
退出状态、CPU/配置/操作数、checksum、线程CPU差值和墙钟窗口、组跨度与汇总。
跨轮及共享/私有表的最终index一致；计时外/proc/vmstat前后没有pswpin/pswpout
增量。二进制、runner、调度脚本及三个表文件摘要运行前后一致，三项私有挂载
卸载成功，没有本次进程或宿主rootfs子挂载残留。

## 结果

下面是 **N份相同固定工作量任务的聚合吞吐因子** `12*T1/T12`。
它不是固定总搜索图的延迟加速比。T12取最早worker开始至最晚worker结束。

| 控制 | 每worker操作数 | 第0轮 | 第1轮 |
| --- | ---: | ---: | ---: |
| 纯计算 | 500000000 | 7.21× | 7.41× |
| 32KiB私有表 | 1000000000 | 8.24× | 8.14× |
| 8MiB私有表 | 100000000 | 2.89× | 2.52× |
| 8MiB文件映射表 | 100000000 | 11.00× | 9.22× |
| 64MiB私有表 | 50000000 | 9.77× | 9.91× |
| 64MiB文件映射表 | 50000000 | 12.04× | 12.03× |

纯计算T1约0.94/0.97秒，T12约1.57/1.56秒，单worker平均记账CPU成本约增加
36.7%/37.7%；起跑跨度约45/43微秒，不能解释组耗时差距。但单次偏短，尚未
同步测量宿主调度/频率，不能直接归因为SMT、降频或某个固定物理核映射。guest
线程CPU时间也不能代替宿主实际执行时间。需要更长控制复测。

8MiB私有表T1约1.53/1.41秒，T12约6.37/6.72秒；同数据文件映射表的扩展明显
不同。这支持进一步调查工作集与共享方式的影响，但还不能断言 DetSim 的主要
问题就是缓存容量。64MiB控制已超过较小缓存条件，不能简单与8MiB因子做“容量
越大越坏”的推论。略超过12的数值是测量/运行状态变化，不是额外物理核或超线性
保证。输入与顺序控制不消除所有系统波动。

全部代码、短测试、反汇编、原始JSON、计时外系统快照和审计在
`build/shared-parallel/resource-scaling-control/`。本轮无产品代码改动。
