# 独立搜索并发对照（2026-10-23）

共享搜索的等待已经拆分，WSL 上同图的任务内 on-CPU 随并发增加约 41%；详见
[CPU 与调度分析](worker-cpu-scaling-2026-10-23.md)。本轮回答另一个问题：没有
共享 frontier、共享池和跨 worker 派发时，固定单-worker 搜索是否仍随并发变慢？

## 设置与计时边界

主机仍为 gpunode，Ryzen 9 3900X，12 核 24 线程，WSL2。使用相同 NP3 诊断
二进制 SHA256 `6d771e15a7cce79dd830abb82dfe054f9303ba5403d0cd4316474fda3956d8af`，
Raft-library fixture、pages/shared、BFS、depth 12、seed 1、rounds 100。
每个任务均为 `parallel 1`，拥有独立协调器、worker、三个目标进程和存储目录。
它们不共享 DetSim 的 frontier 或 CAS pool，但仍共享机器、内核及底层文件系统。

每份任务继承单 CPU affinity，包含协调器及辅助/被控进程，worker placement
仍为 same-cpu。单任务选择 CPU 0；12 份任务分别选择 guest CPU 0..11。
这不同于此前允许协调器在全部 CPU 上运行的单图并行测试，所以不能把两组
结果直接相除或把该控制称为 DetSim 的单图加速比。

所有任务完成 prefix 后等待统一放行；每个 wrapper 精确记录实际 parallel 命令
发送至返回的时间。所有命令返回后才统一放行图验证，避免某一份任务的 Python
验证干扰另一份尚在搜索的任务。原 benchmark 的时间包含新增等待，故不拿它
排名。组区间为 `min(command start)..max(command end)`，包含开始错开与搜索尾部，
不含 prefix、事后图验证和之后的关闭。组之间严格串行运行，没有并行开展别的实验。

## 重复结果

按 1、12、12、1 顺序运行，每组使用全新目录：

| 组 | 独立任务数 | 共同搜索区间（秒） | 每任务 Task 持有时间中位数（累计秒） |
| --- | ---: | ---: | ---: |
| single1 | 1 | 28.0957 | 26.7724 |
| group12 | 12 | 38.9898 | 36.8669 |
| group12b | 12 | 41.8912 | 39.5048 |
| single2 | 1 | 27.6664 | 26.3973 |

以两组单任务和两组 12 任务的平均组区间计算，独立任务聚合吞吐因子为
`12 × 27.8811 / 40.4405 ≈ 8.27`。这表示同一固定工作被独立执行了 12 份，
不是协作搜索同一个图获得 8.27 倍加速，更不是框架的理论上限。

另外试了一组 guest 偶数 CPU 0,2,…,22，12 份任务共同区间 37.9091 秒；只试
一次且未交错复测，不据此断言 SMT/物理拓扑改善或更改默认 placement。
guest CPU 编号不证明它们一一对应不同物理核心。

五个成功组共 38 份搜索，逐份通过 10457 节点、18266 边、18266 尝试边、零重试，
并重新核算下载的规范图 SHA256，均为
`56ccf7cc9b866e62f6da715136eb596719b3f2b101915e93e4cf0c630217717b`。
使用已有同二进制 native reference；其串行边检查仍是首次发现父边投影，完整
带标签图另行比较，不扩大为通用模型正确性证明。

0.5 秒采样中所有组无 swap 用量增长，可用内存最低约 7.17 GiB。记录的 ready、
release、done、post-release 时间通过先后关系检查。worker cycle 记录全部完成
Task/Done 匹配；Task 持有时间是墙钟区间，不能称为 CPU 时间。

## 可支持的判断

即使任务完全不经过共享搜索协调器，每份工作也明显变慢。因此共享 frontier 或
任务通信并不是全部扩展性损失的必要条件。与之前测得的并发 on-CPU 增长相符，
下一步需要同时考虑恢复/捕获本身的成本以及机器、内核和共享文件系统资源。

实验没有区分频率、缓存、带宽、文件系统争用与 Windows 宿主调度；也不能排除
共享探索还有可优化的额外开销。独立任务保留单-worker 的访问顺序和缓存行为，
不等价于把协作搜索简单拆成独立分区，故本对照不是严格硬件天花板。
当前仍不宣称达到接近线性加速。

## 实现验证与证据

DeepSeek-V4.1-Flash / max 准备了私有 wrapper、runner 和假程序测试；主 agent
复核并收紧了规范图必须存在、结束记录身份及时间顺序、进程组所有权三项检查。
首次真实调用在搜索前因 argv 重复脚本名而失败，暴露了假程序解析器没有覆盖的
边界。增加使用真实 benchmark 参数解析器但不启动 tracer 的回归，先复现失败，
修正后 20 项测试通过，再进行上述成功实验。失败运行不计入统计。

已核对远端输入与脚本摘要。六次 namespace 调用（含失败的一次）共 18 项挂载
卸载全部成功；末次检查没有本实验可识别的残留进程或宿主挂载。
Flash 会话完成后已归档。生产代码和宿主系统配置均未修改。
